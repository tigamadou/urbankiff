# Urbankiff : déploiement sur k3s, serveur configuré par Ansible, secrets dans GitHub

> Spec rédigée le 2026-11-16, validée par le développeur le 2026-11-16. Mission devteam (`/devteam:demarrer`), slug proposé
> `k3s-ansible`. Préalable fait : `docs/v1/specs/2026-11-16-publication-depot-public.md` (dépôt public, secrets dans les
> environnements GitHub, serveurs A et B fermés). Inspirée de l'infrastructure du projet steamy, durcie.

## 1. Intention

Remplacer le déploiement actuel (un `docker compose` par application, poussé par `scp` sur un serveur configuré à la
main, secrets dans des fichiers) par :

- un **cluster k3s**, décrit dans le dépôt, qui fait tourner la prod et la preprod ;
- un **serveur reconstructible** : Ansible transforme un VPS nu en nœud prêt, durci, sans étape manuelle ;
- **aucun secret dans le dépôt** : tout vient des environnements GitHub `prod` et `preprod` ;
- **Docker Compose seulement en local**.

Pourquoi maintenant : le serveur applicatif A a été compromis (mai 2026), le Redis de prod a été infecté par un ver
(port public, sans mot de passe) et la base de prod était ouverte à Internet. La prod est arrêtée depuis ; A et B sont
fermés (SSH seul). La plateforme va être modifiée et doit pouvoir absorber plus de trafic : le cluster doit accepter de
nouveaux nœuds.

## 2. Objectifs, non-objectifs, anti-objectifs

**Objectifs**

1. Un nœud k3s unique, **A réinstallé à neuf** en Ubuntu 24.04 LTS, qui porte les namespaces `prod` et `preprod`.
2. Ajouter un nœud = l'ajouter à l'inventaire Ansible et rejouer le playbook. **B** (ancien serveur de base) est le
   futur deuxième nœud.
3. Seuls 22 (SSH par clé), 80 et 443 exposés ; aucun service de données joignable hors du cluster ; chaque service
   authentifié ; flux réseau limités à ce qui est prévu.
4. Déploiement reproductible par version : pré-release `vX.Y.Z-rc.N` → preprod, release `vX.Y.Z` → prod (approbation
   du développeur), images construites une fois et promues sans reconstruction.
5. Sauvegardes hors serveur (Wasabi) : base en continu et quotidienne, fichiers régulièrement ; restauration documentée
   et testée.
6. Restauration des données de prod **préparée et répétée** : script d'inspection de la sauvegarde du 2026-11-16 et
   procédure de restauration, essayés dans une base jetable. La restauration réelle se fait au premier déploiement de
   la prod, hors mission.
7. Preprod démarrable et arrêtable à la demande, avec ses données conservées, **publique** quand elle tourne.

**Non-objectifs**

- Portage des écrans Firebase du panel et correction de la connexion Google de l'api : **chantier séparé**, avant la
  remise en prod (spec de publication, § 9).
- **Le premier déploiement de la prod** (avec la restauration de sa base) : décision du développeur, la mission ne
  déploie que la preprod. Tout ce qu'il faut pour la prod est construit et validé (charts, valeurs, chemins de
  déploiement, procédure de restauration), mais rien n'est déployé dans le namespace `prod` avant la fin du chantier
  séparé.
- Supervision, alertes, centralisation des logs.
- Haute disponibilité du plan de contrôle (trois nœuds de contrôle) : prévue plus tard, pas dans cette mission.
- Tests de bout en bout.
- Rétablir GitHub Actions (bloqué côté compte) : la mission prévoit un chemin sans CI (§ 5.8).

**Anti-objectifs** (échec même si « ça marche »)

- Un secret dans le dépôt, une image, un log ou un argument de commande.
- Un port de base, de cache ou de stockage joignable depuis Internet.
- La preprod qui peut lire ou écrire les données de prod.
- Une donnée de prod perdue ou une sauvegarde corrompue restaurée sans contrôle.
- Un serveur qu'on ne sait plus reconstruire à partir du dépôt.

## 3. Contraintes

- **Serveur A** : 5,8 Go de mémoire, sans swap, 96 Go de disque, aujourd'hui Ubuntu 20.04 (réinstallé en 24.04 par le
  développeur depuis la console de l'hébergeur, Contabo). Les deux environnements y tiennent avec des limites mémoire et
  un quota sur la preprod (§ 5.4).
- **Serveur B** : base de prod arrêtée, pare-feu SSH seul. Il ne fait pas partie du cluster dans cette mission.
- **Dépôt public** : aucun runner auto-hébergé ; GitHub Actions est actuellement bloqué sur le compte (aucune exécution
  créée) : tout ce que fait la CI doit aussi pouvoir se faire depuis le poste du développeur.
- **Poste du développeur** : Mac ARM ; les images de prod sont `linux/amd64` (A est x86).
- **Contrat devteam** : sur l'hôte, seulement `docker`, `make`, `git`, `gh` ; Ansible, Helm, kubectl et les outils de
  validation tournent en conteneur via des cibles `make`.
- **Noms des secrets** : ceux de `docs/v1/infra/secrets.md`, définis par environnement GitHub (`prod`, `preprod`).
- Toute action sur un serveur, une console de fournisseur, le DNS ou les réglages GitHub est faite ou autorisée par le
  développeur.

## 4. Approches

| Approche | Résumé | Retenue |
| --- | --- | --- |
| **A. Charts Helm, déploiement poussé (modèle steamy, durci)** | La CI (ou le poste) construit les images sur GHCR puis appelle en SSH un script de déploiement à commande forcée, qui crée les Secrets à partir de l'entrée standard et lance `helm upgrade --atomic`. | **Oui** : éprouvé sur steamy, compatible avec « secrets dans GitHub », API Kubernetes jamais exposée. |
| B. GitOps (Argo CD ou Flux) | Le cluster applique ce qui est fusionné dans le dépôt. | Non : impose des secrets chiffrés dans le dépôt ou un coffre externe, contraire à « secrets dans GitHub » ; composant de plus à sécuriser sur un petit nœud. |
| C. Manifestes Kustomize | Comme A sans Helm. | Non : pas de rollback `--atomic`, pas de versions de charts, écart avec steamy sans gain. |
| Docker Compose sur le serveur | Un Compose par environnement. | Non : décision du développeur, k3s sur le serveur, Compose en local. |
| Un serveur par environnement | Cloisonnement physique, comme steamy. | Non : la preprod sert peu ; décision du développeur, un cluster, nœuds ajoutés au besoin. |

## 5. Conception

### 5.1 Topologie

- Cluster k3s, **un nœud serveur** (A) au départ. Les nœuds suivants rejoignent en agents ; le passage à trois nœuds
  de contrôle est hors mission.
- Namespaces : `cnpg-system` (opérateur CloudNativePG et plugin Barman Cloud, namespace des manifestes officiels), `plateforme` (cert-manager), `prod`, `preprod`.
- Ingress : Traefik intégré à k3s ; TLS par cert-manager, Let's Encrypt, défi HTTP-01.
- Noms d'hôtes (inchangés côté public) : `urbankiff.com` (Next), `api.urbankiff.com` (api), `panel.urbankiff.com`
  (panel) en prod ; `preprod.urbankiff.com`, `preprod.api.urbankiff.com`, `preprod.panel.urbankiff.com` en preprod.
  **Aucun nom public pour le stockage** (`s3*`, `s30*` supprimés) : les fichiers sont servis par l'api
  (`/file/<nom>`, `?w=30|300` pour les miniatures créées à l'envoi).
- Registre : GHCR, images `ghcr.io/tigamadou/urbankiff-{api,nextjs,panel}` ; charts Helm en OCI sur GHCR.
- Flannel en mode `wireguard-native` dès l'installation, pour que l'ajout d'un nœud chiffre le trafic entre VPS sans
  reconfiguration.

### 5.2 Ansible (`infra/ansible/`)

Lancé par `make infra-ansible LIMITE=<groupe>` dans un conteneur à version épinglée (Ansible, collections de
`requirements.yml`), la clé SSH du développeur transmise par l'agent SSH (`SSH_AUTH_SOCK`), jamais copiée dans
l'image ni dans le dépôt. Inventaire réel `infra/ansible/inventory.yml` **ignoré par git** ; modèle versionné
`inventory.example.yml`.

Rôles, dans l'ordre de `site.yml` (qui vérifie d'abord les variables obligatoires) :

| Rôle | Rôle concret |
| --- | --- |
| `base` | paquets (ufw, fail2ban, unattended-upgrades) ; comptes administrateurs à clé (liste `admin_users` : nom et clé publique, sans adresse e-mail), sudo validé par `visudo` ; **suppression des comptes absents de la liste** ; sshd : mot de passe désactivé, root interdit, `MaxAuthTries 3` ; ufw : 22, 80, 443 ouverts à tous, ports du cluster (6443, 10250, 51820/udp) ouverts **seulement entre les IP des nœuds**, le reste refusé |
| `k3s` | installation à version épinglée, `--secrets-encryption`, `--flannel-backend=wireguard-native`, kubeconfig en `0600` ; nœud serveur ou agent selon le groupe d'inventaire ; jeton de jonction lu sur le serveur, jamais écrit dans le dépôt ; installation de Helm à version épinglée |
| `plateforme` et `cnpg-system` | `plateforme` : cert-manager. `cnpg-system` : opérateur CloudNativePG et son plugin Barman Cloud (pods `app.kubernetes.io/name=cloudnative-pg` et `app=barman-cloud`), à versions épinglées, depuis des **fichiers versionnés dans le dépôt** (pas d'URL distante au moment de l'application) ; ClusterIssuer Let's Encrypt |
| `deploiement` | compte `deploy` verrouillé ; ServiceAccount Kubernetes par namespace avec un Role limité à ce namespace (pas d'administrateur du cluster) ; kubeconfig de ce ServiceAccount ; script `/usr/local/bin/urbankiff-deploy` ; `authorized_keys` à commande forcée et `restrict`, une clé par environnement |

### 5.3 Charts Helm (`infra/helm/`)

Deux charts, versionnés avec la release :

- **`urbankiff-donnees`** (par namespace) : `Cluster` CloudNativePG (PostgreSQL 15, une instance, volume `local-path`),
  archivage WAL continu et `ScheduledBackup` quotidien vers Wasabi (rétention 30 jours), restauration à un instant
  précis par une valeur `postgres.restauration` ; Redis en StatefulSet avec mot de passe (`REDIS_PASSWORD`) et
  persistance AOF ; RustFS en StatefulSet, bucket créé par un Job, copie régulière des fichiers vers Wasabi par un
  CronJob (rclone). Déployé **sans** `--atomic` (volumes).
- **`urbankiff`** (application) : api (gunicorn), workers (`manage.py runworkers`), Next, panel ; Job de migrations en
  crochet `pre-install,pre-upgrade` (`migrate`, `loaddata fixtures/*.json`, `prodseed`) ; Ingress. Déployé avec
  `--atomic --wait`.

Valeurs : `values.yaml` commun, `values-prod.yaml`, `values-preprod.yaml`.

Durcissement, pour tous les pods : `runAsNonRoot`, `seccompProfile: RuntimeDefault`,
`allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true` avec des volumes
`emptyDir` là où une application écrit ; sondes `readiness` et `liveness` ; `requests` et limites mémoire.

**NetworkPolicies** (refus par défaut dans `prod` et `preprod`, puis ouvertures explicites) :

- Traefik → api, Next, panel seulement ;
- api, workers, Job de migrations → PostgreSQL, Redis, RustFS de **leur** namespace ;
- Next (rendu serveur) → api de son namespace ;
- PostgreSQL → Wasabi (sortie HTTPS) ; CronJob de copie → RustFS et Wasabi ;
- aucune politique n'autorise un flux entre `prod` et `preprod` ;
- sortie Internet **par port** (le contrôleur de NetworkPolicy de k3s ne filtre pas par nom de domaine, et le
  remplacer remettrait en cause Flannel avec WireGuard) : 53 (DNS), 443 et 465/587 (SMTP) seulement pour les pods qui en
  ont besoin (api, workers, PostgreSQL, CronJob de copie, Job de migrations) ; aucune sortie pour les autres
  (Next en rendu serveur ne parle qu'à l'api, panel, Redis, RustFS).

### 5.4 Ressources et preprod à la demande

Requêtes et limites mémoire de départ, à ajuster sur mesure :

| Composant | Prod | Preprod |
| --- | --- | --- |
| api (gunicorn) | 300 Mo / 512 Mo | 200 Mo / 384 Mo |
| workers | 200 Mo / 384 Mo | 128 Mo / 256 Mo |
| Next | 256 Mo / 512 Mo | 192 Mo / 384 Mo |
| panel | 32 Mo / 64 Mo | 32 Mo / 64 Mo |
| PostgreSQL | 384 Mo / 768 Mo | 192 Mo / 384 Mo |
| Redis | 32 Mo / 128 Mo | 32 Mo / 64 Mo |
| RustFS | 128 Mo / 256 Mo | 64 Mo / 192 Mo |

`ResourceQuota` sur `preprod` : 1,5 Go de limites mémoire au total. La prod n'a pas de quota mais ses limites
garantissent qu'elle tient avec la preprod et la plateforme (~1 Go) dans 5,8 Go.

`make preprod-arret` met à zéro les Deployments et StatefulSets applicatifs et l'instance PostgreSQL de `preprod`
(hibernation CloudNativePG), en gardant volumes et Secrets ; `make preprod-demarrage` les relance. Les deux passent par
le compte de déploiement de la preprod.

### 5.5 Images

- api : image de prod avec **gunicorn** (le Dockerfile actuel n'a pas de commande de production), utilisateur non
  root, point de santé `/api/health/` ajouté à l'api (réponse 200, vérifie la base).
- Next : image `standalone` actuelle.
- panel : construction **dans** le Dockerfile (étape de build, plus de `build/` copié depuis la CI), servie par un
  serveur statique non root.
- Étiquettes : `sha-<12 caractères du commit>` et `<version>`. **api** : la prod réutilise l'image de la pré-release
  validée (même digest, réétiquetée), jamais reconstruite. **Next et panel** : leurs URL publiques
  (`NEXT_PUBLIC_*`, `REACT_APP_*`) sont inscrites dans le JavaScript à la construction ; ils sont donc **construits
  par environnement**, à partir du même commit, avec les variables GitHub de l'environnement, et étiquetés
  `<version>-<env>`. Choix fait plutôt que de modifier le code des deux fronts pour charger leur configuration au
  démarrage.
- Construction `linux/amd64` par `docker buildx`, en CI comme sur le poste (`make images-publier VERSION=…`, connexion
  à GHCR avec le jeton de `gh`).

### 5.6 Secrets et variables

- Source : environnements GitHub `prod` et `preprod` (inventaire `docs/v1/infra/secrets.md`). Ajouts de cette
  mission : `WASABI_ACCESS_KEY_ID`, `WASABI_SECRET_ACCESS_KEY` (secrets) ; `WASABI_REGION`, `WASABI_BUCKET`
  (variables) ; secret de déploiement `DEPLOY_SSH_KEY`, variables `DEPLOY_HOST` et `DEPLOY_KNOWN_HOSTS`.
  Retraits : `IMGPROXY_KEY`, `IMGPROXY_SALT` (imgproxy supprimé, § 5.9).
- Transport : la CI envoie `NOM=valeur` sur l'**entrée standard** du SSH (jamais en argument) ; le script de
  déploiement valide le format et les clés obligatoires, crée ou met à jour le Secret `urbankiff-secrets` du namespace
  et le Secret de lecture GHCR, puis calcule une empreinte qui force le redémarrage des pods quand un secret change.
- **Sans entrée** (déploiement depuis le poste, § 5.8), le script réutilise les Secrets déjà présents dans le
  namespace : les valeurs GitHub, illisibles depuis le poste, ne transitent jamais par lui.
- Secrets Kubernetes chiffrés au repos (`--secrets-encryption`).
- `REDIS_ENDPOINT` n'est plus une variable : construit dans le chart à partir de `REDIS_PASSWORD`.
- `DJANGO_SUPERUSER_PASSWORD` : mot de passe de l'administrateur créé par `prodseed` sur une base vide (preprod).

### 5.7 Déploiement

Script `infra/deploiement/urbankiff-deploy.sh`, installé par le rôle `deploiement`, appelé uniquement par la commande
forcée SSH :

- commande acceptée : `deploy <version>` (semver ; pré-release refusée en prod), `preprod-arret`,
  `preprod-demarrage` ; verrou `flock` ;
- `helm pull` des deux charts à la version demandée depuis GHCR ;
- `urbankiff-donnees` sans `--atomic`, attente que CloudNativePG soit prêt ; puis `urbankiff` avec `--atomic --wait`
  (le Job de migrations s'exécute avant) ;
- contrôle de santé `https://<api>/api/health/` pendant 2 minutes au plus ; code de sortie non nul sinon.

Migrations : compatibles avec la version N-1 ; jamais annulées par un rollback.

Rollback : automatique si `--atomic` échoue ; sinon redéploiement de la version précédente (`deploy <version>`) ou
`helm rollback` documenté.

### 5.8 Chemins de déploiement : CI et poste

| Étape | CI (`.github/workflows/deploiement.yml`) | Poste du développeur |
| --- | --- | --- |
| Déclencheur | pré-release `vX.Y.Z-rc.N` → `preprod` ; release `vX.Y.Z` → `prod` (environnement GitHub `prod`, approbation) | `make deploiement ENV=<prod|preprod> VERSION=<version>` |
| Images | construction et poussée (preprod), réétiquetage (prod) | `make images-publier VERSION=…` |
| Charts | `helm package` + poussée OCI | `make charts-publier VERSION=…` |
| Secrets | envoyés sur l'entrée standard depuis l'environnement GitHub | non transmis : Secrets du cluster réutilisés |
| Appel | `ssh deploy@$DEPLOY_HOST "deploy <version>" < secrets.env` | `ssh deploy@<hôte> "deploy <version>"` avec la clé de déploiement du poste |

Le **premier** déploiement de chaque environnement exige ses Secrets : il passe par la CI, ou, tant qu'Actions est
bloqué, par `make secrets-cluster ENV=<env>` qui demande au développeur les valeurs en saisie masquée (même
mécanisme que `make secrets-definir`) et les envoie sur l'entrée standard du script de déploiement, sans les écrire
sur disque.

### 5.9 Local (Docker Compose)

- `docker-compose.yml` reste l'environnement de développement local.
- Suppressions : service `imgproxy`, `IMGPROXY_SETUP.md`, `generate_imgproxy_url.py`, variables `IMGPROXY_*` de
  `.env.template`, crochet mort `apps/panel/src/utility/hooks/useSignedUrl.js`.
- Suppressions liées à l'ancien déploiement : `deploys/`, `caddyprod/`, `apps/*/docker-compose-prod.yml`,
  `apps/backup_service/` (remplacé par les sauvegardes du § 5.3), `apps/minio/` (configuration de déploiement MinIO).
- Code obsolète : branche de stockage `BUCKETEER_AWS_*` de `settings.py`, variables `REACT_APP_MINIO_*` du panel si non
  lues.
- L'environnement d'agent devteam (`compose.agent.yml`) est mis à jour en conséquence.

### 5.10 Bascule

1. **Développeur** : réinstallation de A en Ubuntu 24.04 depuis la console Contabo (même IP), puis
   `make infra-ansible LIMITE=noeuds` ; vérification : `make ports-scan HOTE=<A>` → 22, 80, 443.
2. Inspection de la sauvegarde de la base (§ 5.11) et du bucket MinIO, **sur le poste du développeur** (les
   sauvegardes y sont), puis répétition de la restauration dans une base jetable.
3. **Développeur** : DNS des trois noms `preprod.*` vers A (déjà le cas si l'IP est conservée).
4. Premier déploiement de la **preprod** (base vide, `prodseed`, données de démonstration), publique, tests manuels.
5. Mise à jour de `docs/v1/infra/rotation-secrets.md` : retrait des anciennes instances (base de B, volumes MinIO de
   l'ancien A, effacés par la réinstallation).

**Après la mission** (premier déploiement de la prod, une fois le chantier Firebase et connexion Google terminé) :
procédure écrite et répétée par la mission, dans `docs/v1/infra/premier-deploiement-prod.md` :

1. la sauvegarde inspectée est déposée par le développeur dans un préfixe temporaire du bucket Wasabi de la prod
   (chiffrement côté serveur), depuis son poste ;
2. le chart `urbankiff-donnees` crée une base vide ; un Job de restauration ponctuel (valeur `restauration.active`)
   la remplit depuis Wasabi (schéma et données de l'application, sans les rôles), puis le fichier temporaire est
   supprimé de Wasabi ;
3. les objets du bucket sont copiés de la même façon dans RustFS ;
4. le mot de passe de l'administrateur `prodseed` existant est changé ;
5. le développeur fait pointer `urbankiff.com`, `api.urbankiff.com` et `panel.urbankiff.com` vers A.

Ce chemin évite d'ajouter une commande de restauration au compte de déploiement et de copier des données
personnelles sur le serveur hors de Kubernetes.

### 5.11 Inspection de la sauvegarde

Script `infra/restauration/inspecter-sauvegarde.sh` (conteneur PostgreSQL épinglé, base jetable) : restaure la
sauvegarde dans une base temporaire et liste ce qui ne relève pas de l'application : rôles, fonctions et procédures
hors schémas Django, extensions, déclencheurs, `COPY … FROM PROGRAM` dans l'historique, tâches planifiées. Le
développeur valide le rapport avant la restauration de prod. La restauration de prod n'importe que le schéma `public`
et les données des tables Django (`pg_restore --no-owner --no-privileges --schema=public`). Même contrôle pour le
bucket : liste des types de fichiers et des fichiers hors du préfixe `uploads/`.

Le rapport liste aussi les **préfixes d'URL** distincts trouvés dans les champs d'images et de fichiers (`File.url`,
`post.image`, `banner.Media.file`, `scrapper.image`) : l'ancien `FILES_CDN_ENDPOINT` de prod était déjà
`https://api.urbankiff.com/file`, inchangé ; toute URL vers `s3*` ou `s30*` (noms supprimés) est signalée, et le
développeur décide de sa réécriture en validant le rapport. La version de PostgreSQL du chart est alignée sur celle
qui a produit la sauvegarde (en-tête du dump), ou supérieure.

## 6. Ce qui est décidé, ce qui reste au constructeur

**Décidé** : approche A ; un nœud (A) puis ajout de nœuds, B futur nœud ; namespaces `prod` et `preprod` sur le même
nœud ; Wasabi pour les sauvegardes ; preprod sur base vide avec données de démonstration ; preprod avec emails réels
et **sans SMS** (Twilio désactivé en preprod) ; imgproxy supprimé partout ; stockage sans nom public ; Firebase et
connexion Google hors mission ; **seule la preprod est déployée** par la mission, publique ; premier déploiement de la
prod et restauration après la mission, par la procédure du § 5.10 ; Ubuntu 24.04 ; images `linux/amd64` construites en
CI ou sur le poste.

**Choix faits pendant la conception** (à contrôler) : Next et panel construits par environnement (§ 5.5) ; sorties
filtrées par port et non par nom (§ 5.3) ; restauration future par Wasabi et un Job ponctuel (§ 5.10).

**Laissé au constructeur** : versions épinglées (k3s, Helm, cert-manager, CloudNativePG, Ansible, rclone, images de
base) ; découpage exact des templates Helm ; valeurs des sondes ; forme des tests des scripts et du chart ; noms des
cibles `make` intermédiaires.

## 7. Critère de fin

- `make infra-ansible` sur un VPS Ubuntu 24.04 neuf aboutit sans action manuelle ; relancé, il ne change rien.
- Scan externe de A : seuls 22, 80, 443 ouverts ; SSH par mot de passe refusé.
- `helm lint`, rendu des deux environnements et `kubeconform` verts ; tests du script de déploiement verts.
- Preprod déployée depuis une pré-release (ou `make deploiement ENV=preprod` depuis le poste), publique, démarrable
  et arrêtable.
- Prod : rendu Helm et `kubeconform` verts avec `values-prod.yaml` ; rien de déployé dans `prod`.
- Rapport d'inspection de la sauvegarde produit et validé par le développeur ; restauration répétée dans une base
  jetable, avec un décompte de lignes par table égal à celui de la sauvegarde.
- Un test prouve qu'un pod de `preprod` ne joint pas un service placé dans `prod` (pod de test éphémère).
- Une sauvegarde CloudNativePG est visible dans Wasabi, et une restauration à un instant précis dans une base jetable
  a réussi.
- Aucun secret dans le dépôt (`make secrets-scan` à zéro).

Les critères qui exigent le serveur réel (Ansible sur A, scan externe, preprod déployée, sauvegarde visible dans
Wasabi, rapport d'inspection) sont vérifiés **après la fusion de la PR finale**, lors de la mise en service menée avec
le développeur (§ 5.10) : la mission devteam livre le code, les tests et la documentation.

### 8.3 Contrats entre lots

Fixés ici pour que les lots soient indépendants ; un lot qui a besoin d'en changer un s'arrête et le signale.

| Contrat | Valeur |
| --- | --- |
| Inclusion make (socle) | le `Makefile` inclut `$(filter-out make/devteam.mk make/standard.mk make/secrets.mk make/devteam-agent.mk,$(wildcard make/*.mk))` en plus des inclusions existantes |
| Images | `ghcr.io/tigamadou/urbankiff-api:<étiquette>`, `…-nextjs:<étiquette>`, `…-panel:<étiquette>` ; étiquettes `sha-<12>`, `<version>` (api), `<version>-<env>` (Next, panel) |
| api (api-prod) | Dockerfile multi-étapes : **dernière étape inchangée** pour le Compose local (`runserver`), étape nommée `prod` (`--target prod`) avec gunicorn sur le port 8000, utilisateur UID 10001 ; écritures seulement dans `/tmp` ; santé `GET /api/health/` → 200 si la base répond, 503 sinon ; workers : même image, commande `python manage.py runworkers` ; migrations : même image, commande `sh -c "python manage.py migrate && python manage.py loaddata fixtures/admin.json fixtures/mail.json && python manage.py prodseed"` |
| Next (fronts-prod) | port 3000, UID 10001, écritures dans `/tmp` et `/app/.next/cache` ; arguments de construction `NEXT_PUBLIC_BACKEND_URL`, `NEXT_PUBLIC_BACKEND_URL_FRONT`, `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, `BACKEND_URL` |
| panel (fronts-prod) | construit dans le Dockerfile, servi statiquement sur le port 8080, UID 10001, écritures dans `/tmp` ; arguments de construction `REACT_APP_BACKEND_URL`, `REACT_APP_IMAGEKIT_ENDPOINT` |
| Charts (charts) | `urbankiff-donnees` et `urbankiff`, OCI `oci://ghcr.io/tigamadou/charts/<nom>` ; namespaces `prod`, `preprod` ; Secret applicatif `urbankiff-secrets` (clés = noms de l'inventaire), Secret de lecture GHCR `ghcr-pull` ; valeurs `image.etiquette`, `secretsChecksum`, `environnement` (`prod`/`preprod`), `sms.actif` (faux en preprod), `restauration.active`, `restauration.prefixe` ; services `urbankiff-api:8000`, `urbankiff-nextjs:3000`, `urbankiff-panel:8080` ; hibernation preprod par l'annotation CloudNativePG `cnpg.io/hibernation` |
| Serveur (ansible) | utilisateur `deploy` ; kubeconfig `/home/deploy/.kube/<env>` (ServiceAccount `deploy` de chaque namespace) ; configuration `/etc/urbankiff/deploy.env` (`URBANKIFF_ENV`, `GHCR_OWNER`, `NAMESPACE`) ; le rôle installe `infra/deploiement/urbankiff-deploy.sh` en `/usr/local/bin/urbankiff-deploy` ; `authorized_keys` : `command="/usr/local/bin/urbankiff-deploy",restrict` |

| Restauration (restauration) | sauvegarde déposée sous `restauration/<date>/` du bucket Wasabi de l'environnement ; Job du chart (lot charts) qui appelle `pg_restore --no-owner --no-privileges --schema=public` |
